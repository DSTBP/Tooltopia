## 汇报内容

### 研究问题

研究问题的提出应当按照“明确研究主体—构建研究场景—观察并验证问题—凝练研究问题”的顺序展开。整个汇报过程需要逐层建立逻辑基础：先说明研究对象本身是什么，再说明该对象放到什么特定场景中研究，然后通过现实事件和已有学术研究证明该场景下确实存在值得解决的问题，最终据此形成明确、可形式化描述的研究问题。

1. **研究主体：首先明确 “研究的东西是什么”**

   第一步需要明确研究主体，即本项研究直接研究的对象是什么。研究主体应当保持单一、基础和明确，例如：

   - MoE 模型；
   - GitHub 的 commit 机制；
   - 数据库搜索；
   - RAG 等等

   在这一阶段，只描述研究对象本身，不提前加入后续希望实现的安全、隐私、可信等能力。不应直接写成：端到端加密的 GitHub commit 机制、隐私保护的 MoE 模型等等。这些能力属于后续研究问题和实现目标，应当建立在研究主体、研究场景和问题分析之后。

   然后给出研究主体的**基本定义**，使听众能够明确研究对象的边界。例如，如果研究的是 MoE 模型，需要说明 MoE 模型是什么；如果研究的是 GitHub 的 commit 机制，需要说明 commit 是什么，以及它在版本管理体系中的作用。

   其次需要说明研究主体的**结构**，由哪些部分组成，以及这些部分之间是什么关系。例如：MoE 模型的整体架构结构；commit 机制涉及的数据和结构；数据库搜索过程中涉及的主要组成部分。

   在明确结构之后，需要继续说明研究主体如何运行，即研究主体的**运行机制**。需要回答：数据从哪里进入？中间经过哪些步骤？各部分分别完成什么功能？最终产生什么结果？例如，对于 MoE 模型，需要说明模型内部相关组件如何参与计算。

   完成这一部分之后，听众应当能够对研究主体形成基本认知，并理解后续所讨论的问题具体发生在哪一个结构或运行环节。

2. **场景构建：明确“在什么条件下研究这个对象”**

   在解释清楚研究主体之后，需要进一步限定研究场景。研究问题通常并非针对研究主体在所有情况下进行讨论，而是在一个具体的使用环境、部署方式或运行阶段中进行研究。

   例如：对于 MoE 模型，研究场景可以是将其部署到云服务器；对于 GitHub 的 commit 机制，研究场景可以是版本尚未公开之前的私有 commit。

   这一部分需要回答：

   - 我的研究主体在什么具体环境中运行？
   - 谁在使用它？
   - 它处于什么部署方式、使用阶段或交互关系中？

   场景描述应当具体，使后续所有问题都能够明确对应到这一场景。提出研究场景后，需要证明这一场景具有现实依据，避免场景脱离已有研究和真实应用。场景合理性需要从两个方向提供证据。

   - **第一类证据：权威学术论文**

     查找权威论文，尤其是顶会、顶刊论文，证明已有学术研究曾经搭建、讨论或研究过类似场景。汇报时至少需要说明：

     - 论文全名；
     - 期刊或会议；
     - 发表时间；
     - 论文中涉及的具体场景；
     - 该场景与当前研究场景之间的对应关系。

     这一类证据主要用于说明：学术界已经认可这一类场景具有研究价值，并且已有相关研究对这一场景进行了讨论。

   - **第二类证据：真实现实场景**

     除学术论文外，还可说明现实生活中确实存在这一应用方式或部署方式。汇报时需要说明：

     - 现实中的具体使用方式；
     - 相关主体；
     - 真实存在的部署、使用或业务场景；
     - 可靠来源。

     这一类证据主要用于说明：当前构建的研究场景在现实系统中实际存在。

3. **观察发现：分析“这个场景中具体存在什么问题”**

   在明确研究主体和研究场景之后，进入问题分析阶段。这一阶段需要重新回到第一部分已经介绍过的研究主体结构和运行机制，对其进行逐环节分析：

   当研究主体进入上述场景之后，原有结构或运行机制中的哪些位置会出现问题？

   例如，对于 MoE 模型部署到云服务器的场景，可以进一步分析：服务器侧是否可能发生信息泄露；客户端侧是否可能发生信息泄露；云服务器是否能够获得或窃取相关内容。这里不能只停留在“可能存在风险”的描述，需要针对每一个问题分别寻找证据。

   每一个观察发现都需要由两类证据共同支撑：

   - **真实事件案例**，每个案例需要说明事件标题与发生时间、已经公开确认的事实、事件与当前研究对象之间的关联及研究启示，以及具体证据来源。事件概述应只陈述已经公开的事实，包括发生了什么、涉及哪些主体、暴露出什么问题以及造成了什么已公开影响；随后需要将事件与当前研究对象建立明确对应关系，说明该事件暴露出的风险对应当前研究对象中的哪个结构、运行机制或交互环节，以及类似问题如果出现在当前研究场景中会产生什么影响。
   - **学术论文证据**，需要寻找已经明确指出相关问题、分析相关风险，或者基于这些风险提出攻击方案的已有研究。每篇论文需要说明论文全名、期刊或会议、发表时间，并概述论文具体研究了什么问题、发现了什么风险或提出了什么攻击，同时明确这些内容与当前研究对象中具体结构或运行环节之间的对应关系。在此基础上进一步总结论文带来的研究启示，例如某类信息可能泄露、某个参与方可能获得额外信息、某个运行环节可能受到攻击或某种机制可能产生安全影响。

   二者共同用于证明：该问题具有现实影响，并且已经受到学术界关注。

4. **问题归纳：从多个观察发现中提炼核心矛盾**

   在完成真实事件和学术论文分析后，需要对已经发现的问题进行统一归纳。这一阶段需要回答三个问题：

   - 当前研究场景中，哪些信息、组件或计算过程需要受到保护？
   - 哪些参与方可能造成风险？
   - 当前研究主体中哪些结构或运行环节是这些风险产生的关键位置？

   此时应当将前面分散的问题重新对应到研究主体的整体结构中。例如，对于一个包含客户端、云服务器、模型、路由和专家执行过程的系统，可以分别分析这些部分在当前场景中暴露出的风险，然后进一步归纳：现有问题最终集中在哪几个核心安全目标上？

5. **研究问题：明确“最终究竟要解决什么”**

   研究问题必须建立在前面三层逻辑基础之上：研究主体已经明确；研究场景已经通过论文和现实证据证明合理；场景中的问题已经通过真实事件和学术论文证明存在。此时再正式提出研究问题。

   **研究问题**需要同时包含：

   - 研究对象；
   - 研究场景；
   - 参与方；
   - 需要保护的对象；
   - 需要保证的性质；
   - 需要保留的原有功能或效率特征。

   研究问题不能只使用“安全”“隐私”“可信”等宽泛概念，需要明确指出究竟保护什么、保证什么，以及约束条件是什么。例如，可以将研究问题形式化描述为：“研究面向高敏感机构将 top-k 稀疏 MoE 推理外包给独立云服务商的场景。客户端输入包含金融交易、医疗记录、理赔材料、企业邮件或安全告警；云端持有模型并提供推理服务。问题是如何在不泄露客户端输入、服务端模型和 token 级专家路由的条件下，证明路由生成、专家私密选择与专家执行使用同一正确路由和同一已承诺模型，并保留每个 token 仅完整执行 k 个专家的稀疏性？”

   在正式提出研究问题之后，可以进一步将其拆解为**具体实现目标**。比如：

   - 机密性：对于具有相同公开形状的输入，攻击者不能区分输入；客户端除输出外不能恢复模型参数。
   - 完整性：客户端接受输出时，必有 y=F_W(x)，且路由、专家、模型版本和全部规定计算一致
   - 迹线无关性：协议消息、专家扫描、缓冲区形状、访存类别、AMX 指令形状及时间桶只依赖公开参数。
   - 稀疏效率：所有专家可参与固定顺序的轻量私密参数聚合，但完整专家前馈网络仅执行一次，避免退化为全专家安全计算。

通过这一过程，需要依次证明两件事情：

1. 所选择的研究场景具有现实合理性；
2. 所提出的研究问题具有研究必要性。



### 方案汇报

整体逻辑是：首先回到前面已经提出的研究问题，考察已有工作是否已经能够实现这些研究目标，并分析已有方案为什么不能直接满足当前研究需求；随后针对这些不足提出自己的方案，说明方案如何对应前述问题和目标；最后通过与已有工作的功能和性能对比，验证自己的方案究竟解决了哪些已有方案没有解决的问题，以及在性能方面取得了什么改进。

整个方案汇报最终需要回答三个问题：**已有工作为什么不能直接使用？我们的方案具体如何解决这些问题？我们的方案相较已有工作具体改进在哪里？**

1. **已有方案分析：说明“为什么不能直接使用已有方案”**

   提出自己的方案之前，首先需要系统梳理与当前研究问题最相关的已有工作。这里不能只简单罗列相关论文，而需要围绕前面已经明确的研究目标判断：是否已经存在能够实现这些目标的方案，如果存在，这些方案具体实现到了什么程度，又存在哪些限制。

   对于每一个关键已有方案，应当首先给出完整的基本信息，包括论文全名、发表期刊或会议、发表时间，并明确该论文解决的具体问题以及与当前研究问题之间的关系。在此基础上，需要重点解释其**实现原理**，即已有方案究竟通过什么方法实现其目标，核心机制是什么，各部分如何配合，以及其方案成立所依赖的条件是什么。

   这一部分需要让听众真正理解已有方案“是怎么做的”。只有把已有方案的实现原理讲清楚，后面对其缺陷的分析才具有依据。

   完成原理介绍后，需要进一步分析已有方案为什么不能直接用于当前研究问题。缺陷分析应当紧密结合已有方案的具体机制和当前研究目标，主要可以从两种情况展开：

   - 已有方案本身存在缺陷。

     即使按照原论文所设定的场景和目标使用，该方案仍然存在某些不足，使其无法完整满足当前研究所需要的功能或性能要求。此时需要明确指出缺陷具体发生在哪个机制、哪个步骤或哪个目标上，并说明这一缺陷会产生什么影响。

   - 已有方案在原有场景中能够正常工作，但直接迁移到当前研究对象或研究场景后存在适配问题。

     已有方案的原理依赖特定结构、运行方式或假设，而当前研究对象具有不同的结构、机制或目标，直接照搬后会出现适配性的缺陷。此时需要明确说明已有方案依赖什么条件，当前研究场景在哪些方面不满足这些条件，以及直接应用后会导致什么问题。

   因此，对已有工作的分析不能停留在“别人方案不好”这一结论上，而应当形成完整的推导关系：

   **已有方案解决什么问题 → 采用什么实现原理 → 能够实现哪些目标 → 仍然存在哪些缺陷 → 这些缺陷为什么会影响当前研究问题 → 因此当前研究仍然需要新的方案。**

   这一部分承担的是整个方案设计的必要性论证。只有说明已有方案无法完整满足前面提出的研究目标，后续提出自己的方案才具有充分依据。

2. **方案提出：说明“我们的方案具体如何解决前述问题”**

   在明确已有工作的不足之后，再正式提出自己的方案。自己的方案应当直接针对第一部分归纳出的缺陷进行设计，使“已有方案的问题”和“我们的解决方法”形成一一对应关系。

   首先需要给出方案的整体思路，说明方案希望解决什么问题，核心设计思想是什么，以及整体由哪些部分组成。这里需要让听众先获得完整的方案框架，理解各个模块之间的关系，再进一步介绍具体实现。

   随后按照方案的实际执行过程展开说明。需要明确输入是什么，经过哪些步骤，每一步完成什么功能，各部分如何交互，最终产生什么结果。对于每一个关键设计，都应当同时回答两个问题：这一设计具体是如何实现的，以及它解决了第一部分中已有方案的哪个缺陷。

   因此，方案介绍不能只描述“我们增加了什么机制”或“我们设计了什么模块”，还需要建立明确对应关系。例如，当已有方案存在某项功能缺失时，需要说明自己的哪个设计补足了该功能；当已有方案由于直接迁移而出现适配问题时，需要说明自己的方案如何针对当前研究对象的结构或运行机制进行适配；当已有方案存在性能问题时，需要说明自己的设计通过什么机制减少相应开销。

   方案提出部分最终应当形成如下逻辑：

   **已有方案存在缺陷 A → 我们设计机制 A′ 进行解决；已有方案存在缺陷 B → 我们设计机制 B′ 进行解决；已有方案存在缺陷 C → 我们通过相应设计 C′ 完成适配。**

   在介绍完整方案后，还应当重新对应前面提出的研究目标，说明整个方案最终分别实现了哪些目标，使“研究问题—实现目标—方案设计”形成完整闭环。

3. **对比验证：说明“我们的方案相比已有方案的效果”**

   提出方案之后，需要通过与已有工作的直接对比说明方案的改进效果。对比应当围绕前面研究问题中已经提出的目标展开，主要包括功能对比和性能对比两个方面。

   - **功能对比**：我们的方案实现了哪些已有方案没有实现的功能，或者在哪些目标上实现得更加完整。

     这里需要将前面定义的研究目标逐项列出，并分别判断不同方案是否能够满足。例如，对于某一个具体目标，需要说明已有方案是否实现、实现到什么程度，我们的方案是否实现，以及具体改进体现在哪里。功能对比的重点是证明自己的方案补足了已有工作的缺失，因此必须与第一部分中的缺陷分析保持一致。第一部分指出已有方案缺少什么，第三部分就应当明确展示自己的方案如何补上这一部分。

   - **性能对比**：在实现相同或更多功能的情况下，我们的方案在性能方面是否优于已有方案。

     需要选取能够反映方案性能的指标，将自己的方案与已有方案进行直接比较，并根据对比结果说明已有方案的性能问题体现在哪里，自己的方案在哪些方面获得改善。这里需要注意功能和性能之间的关系：如果自己的方案实现了更多功能，还需要说明新增功能是否带来了额外性能开销，以及整体性能表现与已有方案相比如何；如果方案声称具有性能优势，则需要通过具体对比证明这种优势。
